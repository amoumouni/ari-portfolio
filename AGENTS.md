## Branching and Deployment Rules

- `main` is the production branch.
- `development` is the working branch.
- GitHub Pages publishes from the root directory of `main`.
- Never commit directly to `main`.
- Never merge, push, publish, or deploy without explicit approval.
- Never change domain, DNS, or GitHub Pages settings without explicit approval.
- Always verify the active branch before editing.
- Prefer small, focused changes that are easy to review and reverse.
- Use pull requests to review changes before merging into production.

## Layout and Responsive Design

- Support desktop, tablet, and mobile screen sizes.
- Keep the header opaque, never transparent.
- Prevent the header from covering important background content.
- Preserve the Chicago skyline visual identity.
- Maintain consistent backgrounds across website pages.
- Ensure project thumbnails display correctly without unwanted cropping.
- Avoid horizontal overflow and overlapping elements.
- Preserve the existing responsive card layouts unless a change is approved.

## Code Maintenance

- Inspect existing code before making changes.
- Reuse existing styles and components where practical.
- Avoid duplicate or conflicting CSS rules.
- Do not delete files or assets without approval.
- Preserve existing page content and working features.
- Explain significant changes and identify affected files.
- Do not introduce unnecessary dependencies.

## Testing and Quality Assurance

Before proposing a completed change:

1. Check mobile, tablet, and desktop layouts.
2. Verify navigation and internal links.
3. Check image loading and image proportions.
4. Check for layout overflow and CSS conflicts.
5. Test relevant functionality where testing tools are available.
6. Report what was tested and what could not be verified.

## Communication and Approval

- Explain findings clearly.
- Distinguish confirmed defects from suggested enhancements.
- Do not implement unrelated changes.
- Request approval before destructive or production-affecting operations.
- Summarize modified files and explain how to preview changes.
- Never claim a change has been tested or deployed unless verified.

## Priority

Maintain the approved ALM visual identity while improving website usability, accessibility, responsiveness, and reliability.
